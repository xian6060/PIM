PIM-malloc Experiment Report

Alien Cache
改良與 Flush Threshold 實驗

本報告記錄 alien cache 的四個改良步驟：修正 bug、O(1) 查 owner、每個 owner 只拿一次鎖、合併同一頁的 bitmap 讀寫。 每一步都用重寫後的 benchmark 掃描 flush threshold 1 到 64，以 DPU cycles 作為指標。 程式碼在 alien-cache-opt 分支，每一步各一個 commit。

結論摘要

先講結果，細節在後面各節。

主要發現

  • 效能提升幾乎都來自修正 bug 與第 1 步：free 不再掃描所有 thread cache 的串列，總 cycles 從 18.7M / 34.3M 降到約 3.3M / 3.8M。
  • 在原本的設計下，threshold 越大越慢（64 比 1 慢 7–8%），因為批次 flush 沒有分攤任何成本。
  • 第 3 步之後批次處理才真正省下 MRAM 存取（bitmap 讀改寫最多減少 64 倍），但總時間只在 neighbor 模式快 0.2–0.8%，scatter 模式反而慢 2–4%。
  • 因此在這個環境下，threshold 32 不是最佳值。直接釋放（threshold 1）在每組設定都是最快或接近最快。

原因與限制

  • DPU 上 16 個 tasklet 輪流執行，MRAM DMA 的延遲大多被其他 tasklet 蓋過；真正的瓶頸是 pipeline 的指令吞吐量。批次處理省下的 DMA，大致被它多出的管理指令抵掉。
  • UPMEM 的硬體 mutex 沒人搶時只要一條指令，所以「減少拿鎖次數」本身幾乎沒有效益。
  • 所有數據來自 UPMEM SDK 的模擬器（backend=simulator），尚未在實體 DPU 上驗證。

為什麼要重做實驗

舊版報告認為 threshold 32 最佳，但舊實驗量不出 threshold 的影響。

舊 benchmark 的問題

  • 每個 tasklet 只配置 1 個指標，再釋放鄰居的 1 個指標，所以每個 alien cache 最多只收到 1 個指標。threshold ≥ 2 時，free 過程中從不 flush，最後由 tasklet 0 一次清空。
  • 計時用 Host 端的 dpu_launch() 經過時間，包含模擬器本身的開銷，雜訊遠大於要量的差異。
  • 舊報告寫 NR_TASKLETS = 1，實際編譯參數是 16；「best vs worst 差 5.2%」實際為 24.1%。

allocator 本身的 bug

  • bitmap 位元對應錯誤：allocate 用 metadata[3 − k/32] 的第 31 − k%32 位，free 卻用 metadata[k/32] 的第 k%32 位，等於把第 k 塊當成第 127−k 塊釋放。部分釋放時 chunk 會永遠回收不了，size 2048 甚至會耗盡記憶體讓 DPU 當掉。
  • data race：flush 時直接改其他 tasklet 的 bitmap，沒有任何同步。
  • 建立第一個 page 時（prev = NULL）會讀寫 MRAM 位址 0；assert 誤用 =；buddy metadata 的 DMA 大小 268 bytes 不是 8 的倍數。

程式變動

分支 alien-cache-opt，每一步一個 commit，可用 git checkout <hash> 回到任一版本。

0
修正 bug 並重寫 benchmark（aba042a）
free 改成和 allocate 相同的 bit 對應，並加上 double free 檢查；每個 owner tasklet 一把硬體 mutex（uint8_t __atomic_bit ownerMutexes[16]），保護它的 thread cache，allocate、本地 free、alien flush 都要先拿鎖；新 page 先完整初始化再串進串列，root page 不再寫 MRAM 位址 0；修正 assert；DMA 大小補齊到 8 的倍數並對齊緩衝區。這一版維持原本的 alien cache 設計，作為 baseline。
1
O(1) 查出指標的 owner（e5d1b87）
page header 從 24 bytes 擴成 32 bytes，多存 ownerId 與 sizeClassIndex。page 由 buddy allocator 配置、以 pageSize 對齊，所以 page = base + ((p − base) & ~(pageSize − 1))，讀一次 header 就知道 owner，不必掃描 16 個 tasklet × 8 個 size class 的串列。剛好落在 page 開頭的指標是 buddy 直接配置的大區塊，直接交給 buddyFree。
B
benchmark 加入 scatter 模式（28a79a9）
原本每個 tasklet 只釋放鄰居的指標，alien cache 裡永遠只有一個 owner，「依 owner 分組」顯示不出效果。scatter 模式讓每個 tasklet 釋放其他 15 個 tasklet 的指標。第 1 步用同一個 binary 重新量測，讓之後每一步都用同一個 benchmark 比較。
2
每次 flush 對每個 owner 只拿一次鎖（1809a90）
flush 時先讀出每個指標的 owner，用 counting sort 依 owner 分組，每組只拿一次鎖；整批只有一個 owner 時跳過排序。沒有採用「owner 自己來收」的 MRAM 收件匣，因為每個指標要多一次 DMA 寫入與讀取。
3
依 owner 分串列，合併同一頁的 bitmap 讀寫（6fc5e1f）
free 已經讀過 header，所以 enqueue 時就把指標串進該 owner 的串列，flush 不再重讀 header 或排序。同一頁的連續指標先在 WRAM 裡合成一個遮罩，只做一次 bitmap 讀改寫。每個 tasklet 從「自己的下一個 owner」開始 flush，避免所有 tasklet 同時搶 owner 0 的鎖。threshold 1 直接釋放，不經過串列。
4
批次 buddy free：跳過
第 1 步之後，大區塊在 free 時就直接交給 buddy allocator，不會進 alien cache；所有量測中 alien 路徑的 buddy_frees 都是 0，沒有東西可以批次處理。

實驗方法

DPU 端 benchmark：hw/Tests/MicrobenchmarkTest/Device/Main.c；Host 端：hw/Tests/MicrobenchmarkTest/Host/Main.c。

工作負載

  • 16 個 tasklet 各跑 8 輪；每輪先配置 64 個 32-byte 物件，barrier 後再釋放。
  • 每批的前 local% 個物件由 owner 自己釋放，其餘由別的 tasklet 釋放（跨執行緒 free）；每個指標剛好被釋放一次。
  • neighbor：tasklet t 的物件全部由 t − 1 釋放，每個 alien cache 只有一個 owner。
  • scatter：tasklet t 的第 i 個物件由 t − 1 − (i mod 15) 釋放，每個 tasklet 會釋放其他 15 個 owner 的物件。
  • 最後每個 tasklet flush 自己的 alien cache。
  • threshold 掃描 1、2、4、8、16、32、64；每組設定重複 3 次取中位數。

量測與驗證

  • 計時：tasklet 0 在 barrier 之間讀 perfcounter，分別累計 alloc、free、drain 三個階段的 DPU cycles，存進 __host struct BenchmarkResult，Host 用 dpu_copy_from 讀回。
  • 計數器：每個 tasklet 各自累計本地 free、alien enqueue、flush 次數、拿鎖次數、header 讀取次數、bitmap 讀改寫次數，結束時加總；另外統計使用中的 page 數。
  • 驗證：計時前另跑一次驗證。每個配置到的物件寫入唯一標籤，配置完成後逐一檢查，標籤被覆寫代表有配置重疊；全部 flush 完後，所有 bitmap 必須回到全空，否則代表有 chunk 漏掉沒回收。
  • 壓力測試另外涵蓋 size 16 batch 128、size 2048、size 100 batch 100、local 0% 與 100%。

固定參數

NUM_DPUS = 1 (backend=simulator) NR_TASKLETS = 16 mallocableRegionSize = 2 MiB pageSize = 4 KiB bufferSize = 1 KiB sizeClasses = {16, 32, 64, ..., 2048} ALIEN_CACHE_SIZE = 64 compile flags = -O3（含 assert）

分析與後續建議

分析

  • Step 1 的效益最大：原本每次 free 都要沿著串列找 page，跨執行緒 free 甚至要掃描全部 128 個 cache，每一步都是 MRAM 讀取加上一串指令。
  • Step 1 有一處小退步：size 16 且 100% 本地 free 時慢約 6%。這時舊的串列掃描第一個 cache 就命中，新做法每次 free 多一次 8-byte header DMA。
  • Step 3 的 threshold 1 比 Step 1 快，主要是因為 Step 1 的 alien 指標會讀兩次 header（free 時一次、flush 時一次），Step 3 重用了第一次讀到的 owner。
  • 批次處理的上限很低：最理想的 neighbor 模式省下 98% 的 bitmap 讀改寫，總時間也只少 0.8%。

後續建議

  • 在實體 UPMEM 硬體上重跑，確認模擬器的 cycle 模型（尤其是 DMA 與 mutex 的成本）與實機一致。
  • 減少 free 路徑的指令數：DPU 沒有硬體除法器，chunk index 與 assert 裡的 /、% 都是軟體除法；size class 為 2 的冪時可改用位移，計時用的版本可以加 -DNDEBUG。
  • 增加更接近實際應用的工作負載，例如物件跨輪存活、多種大小混合，以觀察延後回收對 page 用量的影響（size 2048 時 threshold 64 用到 432 個 page，threshold 1 只要 240 個）。
  • 如果保留 alien cache，建議預設 threshold 1（直接釋放）；只有在確定是固定鄰居的 producer–consumer 模式時，才考慮 32–64。
