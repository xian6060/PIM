研究動機

原本的跨 tasklet free 需要在多個 thread cache 中做掃描，還可能伴隨全域鎖競爭。 當 free 次數增加時，這些成本會直接放大，形成明顯瓶頸。

這次修改加入 per-tasklet 的 alien cache，將 foreign free 先暫存起來，再批次 flush， 目標是把每次 free 的同步成本轉移成較少次數的集中處理。

  • 降低跨 tasklet free 的即時鎖競爭。
  • 減少每次 free 都要掃描整組 cache 的次數。
  • 用 DPU 端 counter 補足只看總時間時看不到的行為資訊。

實驗方法

1

配置測試環境

使用 UPMEM simulator 執行 Host / Device 程式，避免硬體依賴干擾比較。

2

測量 cross-tasklet free

讓 tasklet free 其他 tasklet 的指標，以模擬最容易出現 contention 的情境。

3

加入 alien cache 與 flush

foreign free 先進入本 tasklet 的 alien cache，累積到門檻後再批次 flush。

4

讀回 DPU counters

記錄 enqueued frees、flushed pointers 與 flush cycles，補足效能觀察的細節。

結果比較

Baseline 19,388 us Alien cache 18,988 us Instrumented 22,935 us
本次量測顯示 alien cache 版本比 baseline 略快，幅度約 2%；而加入 device counters 後， 總時間上升，合理推測是計數與 perfcounter 量測本身帶來額外開銷，因此 instrumented run 不應直接與前兩次做絕對速度比較。

DPU counters 觀察

  • device_enqueued_frees = 15：表示 15 次 foreign free 先進入 alien cache。
  • device_flushed_pointers = 16：flush 時實際處理了 16 個 pointer，顯示最後由門檻觸發一次完整 flush。
  • device_flush_cycles = 27136：flush 階段累計週期數，可用來觀察批次回收成本。

這些 counters 的價值不在於替代總時間，而是在於把「時間花在 enqueue 還是 flush」拆開， 讓後續優化能更精準地指向真正昂貴的路徑。

結論

alien cache 的核心效果是把高頻、分散的 free 同步成本，改成較低頻、集中式的 flush。 在目前 microbenchmark 下，這樣的 batching 已能看到小幅收益。

後續如果要再往下優化，可考慮加入 size-class / owner metadata，避免 flush 時還要對所有 thread cache 做完整掃描。

量測來源：`hw/build/Tests/MicrobenchmarkTest/Host/Microbenchmark_test_host` 的 simulator 執行結果。 報告中的 baseline 與 alien cache 比較值來自先前量測，instrumented run 則是加入 device counters 後的最新執行結果。
